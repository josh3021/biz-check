# biz-check

**우리 서비스가 사업적으로 말이 되는지, AI가 실제 코드와 기획 문서를 직접 읽고 점검해 줍니다.**

"이 가격이 맞나?", "출시 범위가 너무 큰가?", "돈이 남는 구조인가?" 같은 질문을 평소 말로 물으면 됩니다. 개발 용어를 몰라도 읽을 수 있는 쉬운 설명부터, 계산과 대안까지 담은 정밀 분석까지 세 단계로 받아볼 수 있습니다.

> 처음이라면 [설치](#설치)는 개발자에게 한 번만 부탁하세요. 그다음부터는 채팅창에 질문만 하면 됩니다.

## 이런 질문에 답합니다

| 궁금한 것 | 점검 이름 |
| --- | --- |
| 돈 계산과 주문 규칙에 구멍이 없나요? | `logic` |
| 첫 출시에 꼭 필요한 것만 만들고 있나요? | `mvp` |
| 쓰는 돈보다 버는 돈이 많아질 수 있나요? | `viability` |
| 돈 받는 방식(구독·일회 결제)과 가격이 맞나요? | `pricing` |
| 누구를 위한 서비스인지 분명한가요? | `persona` |
| 사람들이 다른 대안 대신 이걸 고를 이유가 있나요? | `competition` |
| 법이나 운영 문제로 사업이 막힐 일은 없나요? | `risk` |
| 잘되고 있는지 숫자로 알 수 있나요? | `kpi` |
| 처음 온 사용자가 얼마나 빨리 가치를 느끼나요? | `aha` |

점검 이름은 외울 필요가 없습니다. 궁금한 것을 그대로 물으면 맞는 점검이 실행됩니다.

## 결과는 3단계로 조절합니다

| 단계 | 누구에게 맞나요 | 무엇을 보여 주나요 |
| --- | --- | --- |
| **쉽게** (`easy`) | 기획자, 대표, 개발을 모르는 누구나 | 표 없이 쉬운 문장으로. 무엇이 문제이고, 사업에 어떤 손해가 되며, 누가 무엇을 하면 되는지 |
| **표준** (`standard`) | 기획자와 개발자가 함께 볼 때 | 점검 항목마다 판정과 근거(코드 위치), 다음 할 일을 표로 |
| **정밀** (`deep`) | 중요한 결정을 앞두고 깊이 따져볼 때 | 표에 더해 계산, 대안 비교, 문제 항목 재확인, 지금/다음/나중 실행 계획 |

단계가 달라져도 **점검하는 내용과 엄격함은 같습니다.** 달라지는 것은 보여 주는 방식뿐입니다. 쉽게 단계로 받아도 근거는 따로 저장되므로 개발자가 나중에 확인할 수 있습니다.

### 같은 문제를 세 단계로 보면

**쉽게**

```
전체적으로 방향은 괜찮지만, 출시 전에 꼭 손봐야 할 것이 2가지 있습니다.

돈 계산과 주문 규칙에 구멍이 없나요? — 7개 중 5개 문제없음
- ❌ 결제 금액을 고객의 휴대폰 안에서 계산하고 있습니다. 앱을 조작하면 금액을 바꿔서
  결제할 수 있어 매출 손실로 이어집니다.
  → [개발팀에 요청] "결제 금액은 우리 쪽 시스템에서 계산하도록 바꿔 주세요."
- ⚠️ 결제 완료 알림이 두 번 오면 주문이 두 번 처리될 수 있습니다. 고객 항의와 환불 업무가 생깁니다.
  → [개발팀에 요청] "같은 결제가 두 번 처리되지 않게 막아 주세요."

먼저 할 일
1. [개발팀에 요청] 결제 금액 계산 위치 변경
2. [직접 결정] 환불 규칙 정하기 — 아직 아무도 정하지 않았습니다
3. [개발팀에 요청] 중복 결제 방지

각 항목의 근거는 개발자용으로 .biz/report.md에 저장했습니다. "더 자세히 보여줘"라고 하면 볼 수 있습니다.
```

**표준**

```
❌ 1 · ⚠️ 1 — 가장 시급: 가격을 클라이언트에서 계산, 콜백 재시도 미처리

### logic (2026-11-25, standard)
| 항목                         | 판정 | 근거                        | 다음 조치                    |
| ---------------------------- | ---- | --------------------------- | ---------------------------- |
| 핵심 루프가 끝까지 연결됨    | ✅   | lib/order/checkout.dart:42  | —                            |
| 가격을 한 곳에서 계산        | ❌   | lib/cart/cart_view.dart:88  | 합계 계산을 서버로 이동      |
| 결제 상태 전이가 멱등함      | ⚠️   | api/payments/webhook.ts:17  | 콜백 재시도 처리             |
```

**정밀** — 표준의 표 아래에 다음이 더 붙습니다.

```
| 루프 단계 | 코드 위치                   | 빠진 것              |
| --------- | --------------------------- | -------------------- |
| 결제      | lib/cart/cart_view.dart:88  | 서버 측 금액 재계산  |

**왜 중요한가**
- 가격 계산: 그대로 두면 조작된 금액으로 결제가 승인됨. 서버에서 합계를 다시 계산하는 코드가 확인되면 ✅로 바뀜.

**모듈 전체**
- 충돌: 가격 정책은 월 구독인데, 비용 계산에는 갱신 실패 시 재시도 비용이 빠져 있음.
- 지금: 서버 금액 계산 → 다음: 중복 결제 방지 → 나중: 연간 요금제
- 신뢰도: 손익분기 판정은 고객 획득 비용 가정에 의존. 이 값 하나가 판정 3개를 바꿈.
```

*(형식을 보여 주는 예시입니다.)*

## 쓰는 법

점검할 프로젝트를 연 상태에서 평소 말로 요청합니다.

| 이렇게 말하면 | 이렇게 됩니다 |
| --- | --- |
| "이 서비스 사업성 점검해줘" | 전체 점검, 저장된 단계로 |
| "가격 정책 괜찮은지 **쉽게** 설명해줘" | 가격만, 쉽게 단계로 |
| "수익성이랑 가격을 **정밀하게** 분석해줘" | 두 가지를 정밀 단계로 |
| "경쟁사랑 비교해줘, 시장 가격도 찾아봐" | 경쟁 점검 + 웹 검색 |

**처음 실행하면 두 가지를 한 번만 묻습니다.** 어떤 언어로 받을지, 어느 단계로 받을지. 고른 값은 프로젝트에 저장되어 다음부터는 묻지 않습니다. 그때그때 "쉽게", "자세히"라고 덧붙이면 그 한 번만 단계가 바뀝니다.

### 결과 읽는 법

| 기호 | 뜻 |
| --- | --- |
| ✅ | 문제없음. 근거가 확인됨 |
| ⚠️ | 일부만 되어 있거나, 확인되지 않은 추정에 기대고 있음 |
| ❌ | 없거나 서로 맞지 않음. 먼저 볼 것 |
| — | 이 서비스에는 해당 없음 |

### 믿고 봐도 되나요

- **지어내지 않습니다.** 모든 판정에는 실제 코드나 문서의 위치가 근거로 달립니다. 프로젝트에 없는 내용은 "정해지지 않음"으로 보고합니다.
- **근거 없는 숫자를 쓰지 않습니다.** 계산에는 `.biz/assumptions.md`라는 표에 적힌 값만 씁니다. 여기에 실제 수치(고객 한 명을 데려오는 데 드는 비용, 결제 전환율, 월 고정비 등)를 채워 넣을수록 결과가 정확해집니다. 직접 적은 값은 덮어쓰지 않습니다.
- **참고용입니다.** 법률·재무·투자 자문이 아닙니다.

## 요구 사항

- 스킬을 지원하는 에이전트 ([설치](#설치) 참고)
- `bash`와 [`ripgrep`](https://github.com/BurntSushi/ripgrep) (`rg`)

## 설치

### Claude Code 플러그인으로 설치

```
/plugin install biz-check --marketplace josh3021/biz-check
```

Claude Code 2.1.275 이상이 필요합니다. 그보다 낮은 버전에서는 `/plugin marketplace add josh3021/biz-check`를 실행한 뒤 `/plugin install biz-check@josh3021`을 실행하세요. 이렇게 설치하면 스킬은 `/biz-check:biz-check`로 호출합니다.

### 공용 스킬 폴더로 설치 (Claude Code, Codex 등)

공용 스킬 폴더에 클론합니다:

```bash
git clone https://github.com/josh3021/biz-check ~/.agents/skills/biz-check
```

그다음 사용하는 에이전트에 연결합니다:

| 도구 | 설정 | 상태 |
| --- | --- | --- |
| Claude Code | `ln -s ~/.agents/skills/biz-check ~/.claude/skills/biz-check` | 확인됨 |
| Codex | 필요 없음. `~/.agents/skills`를 직접 읽습니다 | 확인됨 |
| Gemini CLI | 자동으로 목록에 뜨지 않으면: `ln -s ~/.agents/skills/biz-check ~/.gemini/skills/biz-check` | 미확인 |
| 그 외 에이전트 | 아래 대체 문구를 프로젝트의 `AGENTS.md`에 추가 | 미확인 |

스킬을 지원하지 않는 에이전트용 대체 문구:

```
- For business reviews (MVP, viability, pricing, personas, etc.), read `~/.agents/skills/biz-check/SKILL.md` and follow it exactly.
```

## 명령으로 실행하기

점검할 프로젝트의 루트에서 실행합니다.

```
/biz-check [module...] [easy|standard|deep] [market] [lang=<code>]
```

인자는 순서와 상관없이 줄 수 있습니다. 인자가 없으면 모든 모듈을 저장된 단계로 실행합니다.

| 예시 | 동작 |
| --- | --- |
| `/biz-check` | 모든 모듈, 저장된 단계 |
| `/biz-check easy` | 모든 모듈, 쉬운 문장으로. 이후 기본 단계도 `easy`로 저장 |
| `/biz-check pricing` | 가격 모듈만 |
| `/biz-check viability pricing deep` | 두 모듈, 계산·대안·실행 계획 포함 |
| `/biz-check competition market` | 경쟁사와 시장 가격을 웹에서 찾아 URL과 함께 인용 |
| `/biz-check lang=ko` | 보고서 언어를 한국어로 변경 |

| 옵션 | 효과 |
| --- | --- |
| `easy` | 표 없이 쉬운 문장. 파일 경로, 코드 이름, 개발 용어, 약어를 쓰지 않음 |
| `standard` | 모듈별 판정 표 (`file:line` 근거 포함). 예전 이름 `quick`도 그대로 동작 |
| `deep` | 표에 더해 계산, 대안, ❌/⚠️ 항목 재확인, 모듈 간 충돌과 실행 계획 |
| `market` | 에이전트에 웹 검색이 있으면 경쟁사와 시장 가격을 조사합니다. 이 옵션이 없으면 검색하지 않고 해당 값을 가정으로 표시합니다 |
| `lang=<code>` | 보고서 언어 (`en`, `ko`, `ja`, `zh`, `es`, ...). 프로젝트에 저장됩니다 |

인자로 준 단계와 언어는 `.biz/config`에 저장됩니다. 말로 덧붙인 단계("쉽게", "자세히")는 그 실행에만 적용됩니다. 단계를 한 번도 고르지 않은 프로젝트의 기본값은 `standard`입니다.

## `.biz/` 캐시

첫 실행 때 프로젝트를 스캔하고 루트에 `.biz/` 폴더를 만듭니다. 이후 실행은 이 폴더를 재사용합니다.

| 파일 | 내용 |
| --- | --- |
| `config` | 보고서 언어와 단계 (`lang: <code>`, `level: <easy\|standard\|deep>`) |
| `facts.md` | 프로젝트 사실: 제품, 타깃, 수익 모델, 가격표, 결제 코드 위치 |
| `assumptions.md` | 가정 표: `name \| value \| source` |
| `report.md` | 최신 판정 표, 모듈별 블록. 어느 단계로 실행해도 근거가 여기에 남습니다 |
| `state` | 사실을 마지막으로 동기화한 커밋 |

- **첫 실행**은 언어와 단계를 물은 뒤 전체 스캔을 합니다.
- **이후 실행**은 `state`의 커밋 이후 `git diff`만 확인합니다. 비즈니스와 관련된 변경이 없으면 프로젝트를 다시 읽지 않고 기존 사실을 그대로 씁니다.
- **단계만 바꿔 다시 볼 때**(예: 표준으로 본 뒤 쉽게)는 바뀐 것이 없으면 저장된 판정을 다시 풀어 쓰기만 합니다. `deep`은 다시 판정합니다.
- **`assumptions.md`는 직접 수정하세요.** 직접 적은 값은 덮어쓰지 않습니다.
- 전체 스캔을 다시 하려면 `.biz/`를 삭제하세요.

`.biz/`를 커밋할지는 선택입니다. 팀과 결과를 공유하려면 커밋하고, 로컬에만 두려면 `.gitignore`에 추가하세요.

## 동작 방식

1. `scripts/scan.sh`가 비즈니스 키워드(가격, 결제, 가입, 분석)의 위치만 최대 200줄로 출력하므로, 에이전트가 저장소 전체를 읽지 않습니다.
2. 에이전트가 개요 문서 하나를 읽고 나머지 문서는 grep한 뒤, 찾은 내용을 `.biz/facts.md`에 기록합니다.
3. 선택한 모듈마다 `references/` 아래 체크리스트의 항목당 한 행씩 판정합니다. 판정 방식은 모든 단계에서 같습니다.
4. 판정 표를 `.biz/report.md`에 저장하고, 고른 단계에 맞춰 보여 줍니다.

전체 스캔은 읽기 약 40KB, 명령 호출 약 5회로 제한됩니다(`deep`은 재확인을 위해 20KB, 2회 추가). 설계 결정은 [DESIGN.md](DESIGN.md)를, 에이전트가 따르는 정확한 지시문은 [SKILL.md](SKILL.md)를 참고하세요.

## 폴더 구조

```
biz-check/
├── .claude-plugin/  # 플러그인·마켓플레이스 매니페스트
├── SKILL.md         # 에이전트가 따르는 지시문
├── scripts/
│   └── scan.sh      # 키워드 위치 스캐너
├── references/      # 모듈별 체크리스트
├── DESIGN.md        # 설계 의도와 결정
└── INSTALL.md       # 도구별 설치 메모
```

## 한계

- `biz-check`는 검토 보조 도구이며, 법률·재무·투자 자문이 아닙니다.
- 판정의 품질은 프로젝트의 코드와 문서, 그리고 사용자가 제공한 가정에 달려 있습니다.
- 재무 모델링 도구가 아니며, `market`을 주지 않으면 시장 조사를 하지 않습니다.
